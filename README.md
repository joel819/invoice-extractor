# invoice-extractor

POST a PDF invoice and get validated JSON back (vendor, dates, line items, totals), with a confidence score on every field and arithmetic checks. It runs locally for free.

## What it does

- **Extraction.** Pulls the invoice number, dates, currency, vendor (name, address, tax ID, email), bill-to, every line item across all pages, and the totals (subtotal, discount, tax, tax rate, total).
- **Strict Pydantic schema.**
  - Money is stored as `Decimal`, never float, and returned as a string such as `"2662.00"`.
  - Currencies must be ISO codes, and the due date can't come before the invoice date.
  - Quantities must be positive, and unknown fields are rejected.
  - Both `1,234.50` and `1.234,50` number formats are understood.
- **Arithmetic checks.**
  - Quantity × unit price = line amount.
  - The line amounts add up to the subtotal.
  - Tax matches the tax rate.
  - Subtotal − discount + tax = total.
- **Errors are flagged, never silently fixed.** Sample invoice 04 has a total that's off by 40.00. The API returns the printed total, flags `total_mismatch`, and marks the invoice `needs_review`.
- **Confidence for every field**, from 0 to 1. A value is marked as low confidence when:
  - it doesn't appear anywhere in the PDF text, which catches an LLM inventing a vendor name or misreading a number,
  - it's part of a failed check,
  - the extractor itself reported it as a guess, for example an ambiguous date like 03/04/2026.
  Fields scoring below 0.7 are listed in `low_confidence_fields`.
- **Clear rejections.** Every error returns `{error, message, details}` with a stable error code:

  | Status | `error` | When |
  |---|---|---|
  | 400 | `invalid_request` / `empty_file` | No file field, or an empty upload |
  | 413 | `file_too_large` | Over `MAX_UPLOAD_MB` |
  | 415 | `not_a_pdf` | Wrong extension, or bytes that aren't a PDF |
  | 422 | `unreadable_pdf` / `encrypted_pdf` / `too_many_pages` | A corrupt, locked or oversized PDF |
  | 422 | `no_text_layer` | A scanned, image-only PDF (OCR isn't included) |
  | 422 | `not_an_invoice` | The document isn't an invoice |
  | 422 | `extraction_failed` | Required fields are missing. `details` lists each one |

- **History.** Every extraction is stored in SQLite (`GET /extractions`, `GET /extractions/{id}`).
- **Web page.** Drop a PDF or click a sample. The page shows the fields with confidence percentages, highlights low-confidence ones, and lists the flags and the raw JSON.

## Quickstart

With Docker:

```bash
git clone https://github.com/joel819/invoice-extractor.git && cd invoice-extractor
docker compose up
```

Without Docker (Python 3.11+):

```bash
git clone https://github.com/joel819/invoice-extractor.git && cd invoice-extractor
pip install -r requirements.txt
uvicorn main:app
```

Open http://localhost:8000 and click a sample invoice. The API docs are at http://localhost:8000/docs.

To call the API directly:

```bash
curl -F "file=@sample_invoices/04-math-error.pdf" http://localhost:8000/extract
```

Run the tests with `pytest`. There are 71 tests, and they need no API key and no network access.

## Architecture

```
POST /extract
   │
   ├─ validate_upload        size, extension                         → 400 / 413 / 415
   ├─ pdf_text.read_pdf      %PDF header, encryption, page limit,
   │                         pypdf layout mode (table rows stay on one line) → 415 / 422
   ├─ extract
   │    ├─ GroqExtractor     JSON mode → Pydantic; one repair round with the exact validation errors
   │    └─ rule_extractor    demo mode, and fallback if Groq is down or returns invalid output
   ├─ Invoice (Pydantic)     strict schema                           → 422 extraction_failed
   ├─ checks.run_checks      arithmetic + sanity flags
   ├─ confidence.score       per field: found in text? failed a check? self-reported guess?
   └─ SQLite                 store the full result → GET /extractions
```

```
main.py                  uvicorn entrypoint
app/
  config.py              settings; demo_mode = no GROQ_API_KEY
  errors.py              InvoiceError → {error, message, details}
  schemas/               invoice.py (the schema), money.py (number/date parsing), api.py (responses)
  extract/               pdf_text.py, llm_extractor.py (Groq), rule_extractor.py (demo), prompts.py
  validate/              checks.py (arithmetic), confidence.py (per-field scores)
  pipeline.py            upload → text → extract → validate → score → store
  routers/               /extract, /extractions, /samples, /health
  static/index.html      upload page with highlighted low-confidence fields
sample_invoices/         the 5 PDFs
scripts/                 make_sample_invoices.py, seed.py
tests/                   offline pytest suite; the Groq client is mocked
```

**Design choices:**

- **The PDF text is the ground truth.** An LLM can return well-formed JSON that is wrong. Checking that each extracted value actually appears in the document catches hallucinations that schema validation can't see.
- **The printed values are kept.** The prompt tells the model never to correct the arithmetic, and the checks report mismatches instead of fixing them. A reviewer needs to see what the vendor actually billed.
- **Money is `Decimal` and serialised as strings,** so there are no float rounding errors in totals.
- **Layout-mode text** from pypdf keeps each table row on one line, which makes line items reliable for both extractors.

## Demo mode

**It runs free, with no API keys.**

| Piece | Cost |
|---|---|
| PDF text extraction: pypdf, local | free |
| Database: SQLite in `./data/app.db` | free |
| LLM: Groq free tier. Without a key, the rule-based extractor is used | free |

When `GROQ_API_KEY` is empty, a rule-based extractor parses the invoice. It reads `Label: value` header fields, the line-item table rows and the totals rows. It extracts all 5 samples correctly and suits similar layouts. Unusual layouts are what the LLM extractor is for. Responses show `"mode": "demo"`, and `/health` shows `"demo_mode": true`.

For the LLM extractor, get a free key at https://console.groq.com/keys, put it in `.env` as `GROQ_API_KEY=...`, and restart. If a Groq call fails or returns invalid output twice, the request falls back to the rule-based extractor and returns `"mode": "fallback"`.
